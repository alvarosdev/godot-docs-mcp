## Context

Current tests use only `testing` standard library — manual `if got != want { t.Errorf(...) }` assertions and real files on disk via `testdata/` directories. There are no interfaces between `internal/docs`, `internal/tools`, and `internal/resources`, so every consumer takes `*docs.DocStore` as a concrete type. This forces disk I/O in all tests and prevents isolated unit testing of tool/resource handlers.

See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- All test assertions use testify (`assert.Equal`, `require.NoError`, `mock.On().Return()`)
- Tool and resource handlers are tested with a mock `DocStoreReader`, never touching disk
- Mocks are generated by mockery from a single interface, not hand-written
- Mock files live alongside the interface they implement (`store_mock.go` in `internal/docs/`)
- mockery runs as a `tool` in `go.mod` — not a global install, not a runtime dependency
- No `gomock`, no `any`, no `Anything()` — every mock call is configured explicitly with `.On("Method", exactArgs).Return(exactValues)`
- Only public functions are tested (package-level exported API surface)
- Legacy `testdata/` is removed for tools/resources (docs store tests keep a minimal `testdata/`)

**Non-Goals:**
- Integration tests (server starts, real HTTP calls, real MCP protocol)
- Test coverage metrics or thresholds
- Mocking `*mcp.Server` or `*mcp.Tool` — those are real SDK objects, not mocked
- Adding interfaces beyond the single `DocStoreReader` needed for testing
- Changing `cmd/godot-mcp-server/main.go` — the concrete `*DocStore` satisfies the interface implicitly

## Decisions

### 1. Single `DocStoreReader` interface instead of per-consumer interfaces

```go
// internal/docs/store.go
type DocStoreReader interface {
    Get(key string) (string, bool)
    Size() int
}
```

**Why**: `tools` and `resources` both need only `Get`. `Size` is useful for test assertions. A single interface in the defining package follows the Go convention (interfaces belong with the data, not the consumer). One mock file instead of two.

**Alternatives considered**:
- Per-consumer interfaces (`tools.StoreReader`, `resources.StoreReader`) — rejected; duplicates the same 2 methods, generates 2 mock files for identical behavior
- No interface, keep using `testdata/` disk files — rejected; couples tests to filesystem, makes tests slower and harder to maintain

### 2. `.mockery.yml` with explicit interface listing instead of `//mockery:generate` directives

```yaml
all: false
template: testify
packages:
  github.com/alvarosdev/godot-docs-mcp/internal/docs:
    config:
      dir: "{{.InterfaceDir}}"
      filename: "store_mock.go"
      pkgname: "{{.PackageName}}"
      structname: "Mock{{.InterfaceName}}"
    interfaces:
      DocStoreReader: {}
```

**Why**: One interface, one config entry. Centralized control — to regenerate mocks, run `go tool mockery`. Directives (`//mockery:generate: true`) add doc-comment noise to production code. For a single interface, a 10-line YAML file is simpler.

**Alternatives considered**:
- `//mockery:generate: true` directive on the interface — rejected; doc comments on interfaces are part of the public API surface, adding tooling directives there mixes concerns
- `go:generate` comment in a `generate.go` file — rejected; requires remembering to re-run manually, whereas `go tool mockery` is explicit and CI-enforceable

### 3. `go.mod` tool directive instead of global `go install`

```bash
go get -tool github.com/vektra/mockery/v3@latest
# go.mod gains: tool github.com/vektra/mockery/v3
```

**Why**: Pins mockery version in `go.mod` + checksum in `go.sum`. Every dev and CI gets the same version. `go tool mockery` runs the cached binary. `go build` ignores it — zero impact on the production binary.

### 4. testify assertions replace all manual error handling

Before:
```go
if got != want {
    t.Errorf("got %q, want %q", got, want)
}
```

After:
```go
assert.Equal(t, want, got)
```

**Why**: testify is the de facto standard for Go test assertions. `assert` for soft failures (continue test), `require` for hard failures (abort test). Mock expectations use `mock.On("Method", args...).Return(values...)` with explicit arguments — no matchers.

### 5. Test file structure: `_test.go` + `_mock.go` alongside source

```
internal/docs/
├── store.go           ← DocStore + DocStoreReader interface
├── store_mock.go      ← generated: MockDocStoreReader
├── store_test.go      ← testify: NewDocStore, Load, Get, Size
├── versions.go
├── versions_test.go   ← testify: LoadVersionMetadata
├── validate.go
└── validate_test.go   ← testify: ValidateDocPath, ResolveDocPath (no mock)

internal/tools/
├── navigation.go
├── navigation_test.go ← testify + MockDocStoreReader: 3 tool handlers
└── (no testdata/)

internal/resources/
├── docs.go
├── docs_test.go       ← testify + MockDocStoreReader: handler + parseVersionPrefix
└── (no testdata/)

internal/server/
├── server.go
└── server_test.go     ← testify + t.Setenv: LoadConfig, New
```

**Why**: Same-directory layout keeps test context close to source. `_mock.go` suffix signals generated code at a glance.

### 6. `testdata/` retained only for docs store tests

The `DocStore` tests need real files to verify `Load()` walks directories correctly. The tools/resource tests use `MockDocStoreReader` and don't need `testdata/`.

## Risks / Trade-offs

- **[Risk] mockery version drift**: mockery v3 → v4 could break generated code format. → **Mitigation**: pinned version in `go.mod` tool directive. Regenerate only when intentionally upgrading.
- **[Risk] Generated mocks diverge from interface**: dev modifies interface, forgets to re-run mockery. → **Mitigation**: CI step `go tool mockery && git diff --exit-code` fails the build if mocks are stale.
- **[Trade-off] Generated code committed to repo**: `store_mock.go` is auto-generated but tracked in git. → Acceptable — generated mocks are small (~30 lines) and reviewing them catches generation bugs. Alternative is generating in CI with no commit, which hides mock issues until PR time.
- **[Trade-off] One interface, two methods**: `Get` and `Size` are in `DocStoreReader`. If a future consumer needs `Load`, it won't be in the interface. → Add `Load` to the interface or create a separate one then. YAGNI — solve it when the need arises.

### 7. Project rebranding: `godot-mcp-docs-http` → `godot-docs-mcp`

**Why**: The old name `godot-mcp-docs-http` was a fork of Nihilantropy's Python project. The rewrite is 100% Go with zero Python code — it's a standalone project, not a fork. The new name `godot-docs-mcp` drops the redundant `-http` (the server supports both stdio and HTTP) and uses the conventional `mcp` suffix.

**What changes**:
- Git remote: `git@github.com:alvarosdev/godot-mcp-docs-http.git` → `git@github.com:alvarosdev/godot-docs-mcp.git`
- Docker images: `ghcr.io/alvarosdev/godot-mcp-docs-http` → `ghcr.io/alvarosdev/godot-docs-mcp`
- LICENSE: `Copyright (c) 2025 Nihilantropy` → `Copyright (c) 2026 Álvaro G.` (code is new, no original code remains)
- README: attribution to Nihilantropy's original idea, all URLs updated
- `deploy/Dockerfile`: deleted (Python, obsolete)
